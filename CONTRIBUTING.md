# Contributing

## Before opening a change

- Search existing issues and discussions.
- Identify the subsystem affected.
- Explain the problem, expected behavior and compatibility impact.
- Update relevant specifications and examples.
- Add tests or conformance cases when behavior changes.

## Architecture changes

Changes to subsystem boundaries, capability semantics, manifest compatibility or execution semantics require an Architecture Decision Record (ADR) in `docs/decisions/`.

## Pull requests

Keep pull requests focused. Do not mix unrelated formatting, refactoring and behavior changes. Clearly mark proposals that are not implemented.
